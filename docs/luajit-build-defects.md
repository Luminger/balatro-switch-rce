# Balatro's LuaJIT build: four defects, one cause

The Switch build of Balatro ships **LuaJIT 2.1.0-beta3** (the `megasource-nx`
LÖVE port, JIT disabled). Four things behave differently from any LuaJIT you
have used on a desktop, and three of them produce wrong values or kill the
process with no Lua-visible error. If you write Lua against this title, these
are operational rules, not trivia.

All addresses are from the exact 1.0.1f `main` NSO; the 1.0.1o offsets are in
`src/bl/offsets.lua`. Every behaviour below was measured on hardware.

| # | defect | symptom | rule |
| --- | --- | --- | --- |
| 1 | `lj_vm_ffi_call` has no body | calling a cdata function pointer executes `UDF #0` and kills the process | never call cdata; use `love.ffi.declare` |
| 2 | 64-bit literals are not literals | `0ULL` is a *number* equal to that literal's constant-table index | no `ULL`/`LL` literals; use `ffi.cast` + arithmetic |
| 3 | 64-bit cdata equality is broken | `ffi.cast("uint64_t",5) == ffi.cast("uint64_t",5)` is **false** | use `love.ffi.u64_eq` / `u64_is_zero` |
| 4 | Lua metamethods on cdata are fatal | first use of a Lua `__call`/`__tostring`/… on a ctype kills the process | use `love.ffi.metatype`, which refuses those |

## The root cause

**The VM was generated by `buildvm` with the DynASM `FFI` conditional off,
while the C library was compiled with `LJ_HASFFI=1`.** So every construct
whose implementation lives inside `.if FFI` in `vm_arm64.dasc` is missing
from the interpreter, while the C code that calls it is present and
reachable. `ffi.cdef`, `ffi.new`, `ffi.cast`, `ffi.sizeof`, `ffi.string`,
`ffi.copy` and all cdata loads/stores work fine. `JIT` is off by the same
mechanism, which is what the *"JIT compiler permanently disabled by build
option"* string in the binary refers to.

### The dispatch table proves it, and validates itself

`lj_bc_ofs` is a `const uint16_t[97]` of offsets from `lj_vm_asm_begin`
(`0x71000538b0` in a flat 1.0.1f image), used as
`dispatch[i] = lj_vm_asm_begin + lj_bc_ofs[i]`. An opcode whose DynASM body
is conditioned out emits nothing, so its dispatch entry collapses onto the
next opcode's handler. Every JIT-only opcode does exactly that:

```
JFORI==FORL==IFORL=7100   JFORL==ITERL==IITERL=7240   JITERL==LOOP==ILOOP=7292
JLOOP==JMP=7316           FUNCF==IFUNCF=7348          JFUNCF==FUNCV==IFUNCV=7412
JFUNCV==FUNCC=7544
```

and so does the one FFI-only opcode:

```
[39] KSTR   = 3496      own handler, intact
[40] KCDATA = 3540      body is entirely inside `.if FFI` -> not emitted
[41] KSHORT = 3540      same offset: KCDATA dispatches into KSHORT
```

The shared handler is upstream `BC_KSHORT` verbatim:

```
sxth w28,w28            ; sxth RCw, RCw   <- RD = the KGC constant index
add  x8,x28,x24         ; add TMP0, RC, TISNUM
str  x8,[x19,x27,lsl#3]
<ins_next>
```

while the intact `BC_KSTR` still has its own body (`mvn x28,x28` /
`ldr x8,[x20,x28,lsl#3]` / `mov x9,#-0x5` = `movn ~LJ_TSTR` /
`add x8,x8,x9,lsl#47` / `str`). The cdata-tagging idiom — `movn #0xb` plus
`add …,lsl #47` — appears nowhere in the image.

**That is defect 2.** A 64-bit literal compiles to `BC_KCDATA`, whose `RD`
operand is the index of its constant; running `KSHORT` instead sign-extends
that index and stores it as a number:

```lua
return tostring(0ULL)                        --> "1"    type "number"
local a=7ULL local b=7ULL return a..","..b   --> "0,1"
```

(`return tostring(7ULL)` gives `"1"` because the string `"tostring"` takes
constant slot 0.) Build 64-bit constants like this instead:

```lua
local U32  = 4294967296
local word = ffi.cast("uint64_t", 0xbadc0ffe) * U32 + 0xe0ddf00d
```

### Defect 1 is the same mechanism on a global label

In `vm_arm64.dasc` the label `->vm_ffi_call:` is emitted *outside* `.if FFI`
while its whole body is inside. With FFI off the symbol still resolves — to
the next address, with zero bytes of code — which is why it lands on eight
bytes of inter-function alignment padding at `main+0x56ef8`, between a `ret`
at `+0x56ef4` and the next function at `+0x56f00`. Its single caller is
`lj_cf_ffi_meta___call` (`main+0x460f0`) at `+0x46994`.

Note what this means: that function has `lj_ccall_func` and `ccall_set_args`
**inlined and fully working** — the build marshals every argument class
correctly into a `CCallState` and then calls into padding. Only the dispatch
is missing, which is what `src/bl/ffi_call.lua` rebuilds.

`ffi.load` and FFI callbacks are separately stubbed (*"no support for loading
dynamic libraries for this OS"*, *"no support for callbacks on this OS"*), and
the title's NPDM grants no `CreateCodeMemory`/`ControlCodeMemory`/
`SetProcessMemoryPermission` while `.text` is R-X — so neither patching that
call nor loading native code of your own is possible on a retail console.

### Defect 3 is a missing three-instruction block in `BC_ISEQV`

Upstream, right after `asr TMP0, CARG1, #47`:

```
.if FFI
  cmn  ITYPE, #-LJ_TCDATA
  ccmn TMP0,  #-LJ_TCDATA, #4, ne
  beq  ->vmeta_equal_cd           ; -> lj_meta_equal_cd()
.endif
  cmp  CARG1, CARG3
```

In the shipping image, `asr x8,x0,#0x2f` is followed *directly* by
`cmp x0,x2`. So cdata equality never reaches `lj_meta_equal_cd`: it degrades
to comparing the boxed object pointers, and then takes an `__eq` path
restricted to tables and userdata. Two distinct cdata holding the same value
compare unequal. `<`, arithmetic and `tonumber` are unaffected, because they
route through C arithmetic metamethods that do exist.

### Defect 4 is two missing guards in `->cont_dispatch`

`lj_meta_tailcall()` is how a C function hands control to a **Lua**
metamethod: it rewrites the frame and installs a continuation value of
`LJ_CONT_TAILCALL`, which is **0**. `->cont_dispatch` (`main+0x55a64`) is
supposed to special-case small continuation values:

```
measured                           upstream
+0x55a64 ldur x2,[x17,#-0x10]      ldr LFUNC:CARG3,[RB,FRAME_FUNC]
+0x55a68 ldur x0,[x19,#-0x20]      ldr CARG1,[BASE,#-32]     <- the continuation
+0x55a6c mov  x3,x19               mov CARG4, BASE
+0x55a70 mov  x19,x17              mov BASE, RB
+0x55a74 and  x2,x2,#0x7fff..      and CARG3, CARG3, #LJ_GCVMASK
         ***  MISSING  ***         .if FFI: cmp CARG1, #1
+0x55a78 ldur x21,[x3,#-0x18]      ldr PC,[CARG4,#-24]
+0x55a7c ldr  x2,[x2,#0x20]        ldr CARG3, LFUNC:CARG3->pc
+0x55a80 add  x8,x27,x28           add TMP0, RA, RC
+0x55a84 stur x26,[x8,#-0x8]       str TISNIL,[TMP0,#-8]
         ***  MISSING  ***         .if FFI: bls >1
+0x55a88 ldur x20,[x2,#-0x48]      ldr KBASE,[CARG3,#PC2PROTO(k)]
+0x55a8c br   x0                   br CARG1
```

Upstream's `1:` handles `cont == 1` (return from an FFI callback) and
`cont == 0` (tailcall from a C function, which goes to `->vm_call_tail`).
Here neither guard exists, so **`br x0` branches to address 0** and the
process dies instantly. Every `lj_meta_tailcall` caller is therefore fatal:

| caller | fatal when |
| --- | --- |
| `ffi_index_meta` | cdata `__index`/`__newindex` is a **function** |
| `ffi_meta___call` | cdata `__call` |
| `ffi_meta___tostring` | the ctype has a Lua `__tostring` |
| `ffi_pairs` | cdata `__pairs`/`__ipairs` |
| `lj_carith_meta` | any cdata arithmetic or comparison metamethod in Lua |

## What still works — verified, not assumed

The model says only `.if FFI` paths are missing, which predicts that these
survive. They do, on hardware:

| path | why it is safe |
| --- | --- |
| table `__tostring`, `__call`, function `__index` | `tostring` is an assembly fast function whose `FFH_TAILCALL` is handled by `->fff_fallback`'s own `bne ->vm_call_tail`, which is not FFI-conditional |
| `ffi.metatype(ct, {__index = <table>})`, **including methods** | `ffi_index_meta` only tailcalls when the metamethod is a function; a table `__index` is resolved by `lj_meta_tget` in C |

So cdata objects with methods are available — put them in a table `__index`:

```lua
local ct = love.ffi.metatype("my_t", {           -- guarded wrapper: refuses
    __index = {                                   -- every fatal shape
        konst  = 42,
        method = function(self) return self.v end,
    },
})
local o = ct(7)
print(o.v, o.konst, o:method())                   -- 7  42  7
```

`love.ffi.metatype` raises a Lua error for a function metamethod or any of
the arithmetic/comparison/`__call`/`__tostring`/`__pairs` shapes, which is
the difference between a stack trace and a console reboot.
